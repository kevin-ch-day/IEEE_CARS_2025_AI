\section{Methodology}

\subsection{Study Design and Evidence Window}

This study performs a descriptive build-aligned analysis of 15 consumer Android apps on static exposure, runtime behavior, and the relationship between those layers. The unit of inference is the selected app-build group: package name, version code and name, base APK hash, split-APK identity, contributing static run, and selected dynamic runs.

The collection used a non-root Motorola Moto G 5G (2024) running Android 15, without app modification, privileged instrumentation, TLS interception, or payload inspection. Evidence was selected from June 26 through July 9, 2026 UTC as a recency, build-alignment, and provenance control, not a longitudinal repeatability experiment. Apps are grouped by primary function (News, Social Media, Messaging, and Professional Networking) for descriptive visualization only, not as statistical strata.

\subsection{Static and Runtime Evidence}

Static analysis used the harvested base and split APK artifacts for each selected build. Reported variables include dangerous permissions, high- and medium-severity findings, unguarded-export findings, network and storage-related findings, privacy and platform findings, and MASVS-aligned categories \cite{owaspMasvs2024}. Unguarded-export findings are High- or Medium-severity detector rows whose titles indicate a missing permission or a weak guard; they count finding rows, not unique Android components.

The runtime analysis used evidence packs associated with the packages and PCAP-derived metadata. The captures were classified as strict-idle (quiet foreground baselines), quiescent foreground (QFG; no-touch foreground with continued app-driven activity) or interactive (user-facing behavior). Reported variables include duration, PCAP volume, packet rate, retained DNS/SNI hostname breadth, and baseline-relative changes when comparable baseline and interactive evidence were available. Hostname breadth is the per-run union of up to 10 retained DNS query names and up to 10 retained TLS-SNI names, not an exhaustive inventory of endpoints. Retained interactive DNS/SNI hostnames were matched by exact or subdomain relation against tracking-oriented categories in a pinned Disconnect services list (commit \texttt{22c7d616}); a documented per-app set of registrable domains (eTLD+1 values) was excluded from the third-party count \cite{disconnectTrackingProtection}.

\subsection{Build Selection and Evidence Alignment}

The qualification policy $P$ is the historical technical validation rule used for the submitted cohort. A dynamic run qualifies under $P$ when it has a nonempty run identifier, \texttt{valid\_dataset\_run} status, required protocol metadata (profile, sequence, and interaction level), duration of at least 180\,s, at least 20 analysis windows of width 10\,s and stride 5\,s, a PCAP of at least 50\,000\,B (10\,000\,B for qualifying connected or text-messaging captures), and a usable PCAP analysis or an explicit no-traffic result.

The qualifying runs are grouped by package, version code and name, and base APK hash. One build group per app is then chosen by an ordered ranking on readiness, presence of both baseline and interactive evidence, capped class coverage, total valid run count, PCAP count, QA-valid count, recency, match to the then-current install, and version code. Static and runtime observations are integrated only for the same selected build (Algorithm~\ref{alg:build-aligned-selection}).

\begin{algorithm}[!t]
\caption{Build-Aligned Static-Runtime Evidence Selection}
\label{alg:build-aligned-selection}
\begin{algorithmic}[1]
\REQUIRE cohort $A$, 14-day window $W$, static set $S$, dynamic set $D$, qualification policy $P$
\ENSURE aligned app-build rows, excluded/deferred rows, source data, checksums
\FOR{each app $a \in A$}
  \STATE retrieve candidate dynamic runs for $a$
  \STATE retain runs satisfying technical qualification policy $P$
  \STATE group runs by normalized package, version code/name, and base APK SHA-256
  \STATE summarize evidence-class coverage and readiness for each group
  \STATE select one group using the ordered build-ranking policy
  \STATE resolve static evidence in $S$ for the selected build
  \IF{static and dynamic identities do not align}
    \STATE exclude or defer $a$; persist the reason; continue
  \ENDIF
  \STATE validate the selected dynamic evidence against reporting window $W$
  \STATE preserve strict-idle, QFG, and interactive classes separately
  \STATE compute static exposure and runtime behavior summaries
  \STATE add the aligned app-build row and provenance
\ENDFOR
\STATE compute descriptive cross-layer profiles and app-level associations
\STATE export aligned rows, excluded/deferred rows, source data, and checksums
\end{algorithmic}
\end{algorithm}

\subsection{Integrated Analysis and Reproducibility}

\emph{Risk posture} denotes evidence-supported conditions that may create or enlarge opportunities for privacy or security harm, not a calibrated probability of exploitation or realized harm. Static and runtime indicators are interpreted jointly and are not collapsed into a single score.

The dispersion of runtime within the window is summarized as the interquartile range (IQR) of the interactive packet rate per-application for applications with at least three selected interactive captures; this secondary measure characterizes the spread within the window rather than the longitudinal repeatability. The reported median packet-rate shift is the app-level median of $\log_2[(I+1)/(B+1)]$, where $I$ is the interactive median packets/s and $B$ is the strict-idle median if that class is present and the QFG median otherwise. In this cohort, only TikTok lacks a selected strict-idle capture and, therefore, uses QFG as the baseline $B$. Cross-layer profiles use a median split: higher static exposure is high- and medium-severity finding volume at or above the cohort median (52), and higher runtime activity is interactive retained-hostname count at or above the cohort median (12); ties are assigned to the higher group. These profiles are cohort-relative and are not a composite risk score.

PCAP processing is limited to metadata and derived transport indicators; message bodies, cookies, authorization headers, private account content, and decrypted TLS payloads are not inspected. Reproducibility artifacts include the selected-build manifest, source CSVs, generated tables and figures, inclusion and exclusion records, SHA-256 checksums, and the pinned Disconnect list.

\subsection{Limitations}

The study is limited to 15 apps, one Android 15 physical device, one collection and network environment, selected interaction scenarios, and the static detectors available. The consistency of the device and environment improves the comparability within the study but limits the generalization between OEM implementations, Android versions, hardware, and networks. Runtime observations are scenario-bounded and do not establish exhaustive app behavior; unequal capture depth may affect app-level precision. Multiple captures characterize within-window behavior; the single evidence window does not establish temporal repeatability.

The non-root design without MITM interception prevents inspection of encrypted payload semantics, so elevated packet rate or transfer volume may reflect media delivery, synchronization, telemetry, advertising, keepalive traffic, or privacy-sensitive exchange. A Disconnect blocklist match indicates an association with categorized infrastructure; it does not establish private-data leakage. Static finding counts are tool-dependent exposure indicators, not measures of exploitability, MASVS compliance, or privacy harm. Observed runtime activity does not demonstrate malicious behavior, and limited activity does not establish low risk.
