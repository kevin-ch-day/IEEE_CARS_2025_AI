\section{Introduction}

Consumer Android apps routinely mediate communication, news consumption, social interaction, and access to personalized services. These capabilities often combine sensitive permissions, exported components, embedded SDKs, cloud services, and encrypted network traffic, creating multiple surfaces through which privacy and security concerns can emerge. Platform permission controls and Google Play Data Safety disclosures provide useful context \cite{androidPermissions2026,googlePlayDataSafety2026}, but neither substitutes for technical evidence tied to the specific app build being evaluated. This distinction is particularly important for frequently updated consumer apps, where static artifacts and runtime observations can otherwise be collected from different versions and interpreted as though they describe the same software.

This paper investigates how build-aligned static exposure indicators and runtime network observations can jointly characterize privacy and security risk posture. Here, risk posture denotes evidence-supported conditions that can create or enlarge opportunities for privacy or security harm; it is not a calibrated probability of exploitation or realized harm. Rather than treating static findings or runtime activity as stand-alone measures of risk, the study examines where the two evidence layers reinforce one another and where they reveal different aspects of the same selected build. The study is organized around three research questions.
\begin{itemize}
    \item RQ1: Which static exposure patterns appear in the selected app builds?
    \item RQ2: How does runtime behavior vary across strict-idle, quiescent foreground (QFG), and interactive classes for those builds?
    \item RQ3: Where do the layers agree or diverge, and how should those divergences inform review without a composite score?
\end{itemize}

A single evidence stream is insufficient for this purpose. Static analysis can identify packaged exposure, including permissions, component configuration, and detector findings, but it cannot establish which behaviors occur during execution. Runtime observations can capture traffic volume, communication intensity, and interaction-driven change, but are scenario-bounded and cannot reveal encrypted payload semantics in the non-root, non-MITM setting used here \cite{sutter2024dynamic}. Data Safety labels and privacy-configurable SDKs provide additional privacy context, but also do not replace build-specific technical evidence \cite{arkalakis2024datasafety,khandelwal2024privacylabels,zhang2024privacysdks}. Combining these perspectives therefore requires both evidence alignment and careful separation between potential exposure and observed behavior.

We present a 15-app study using ScytaleDroid, a database-backed platform that links APK harvests, hashes, static findings, runtime evidence packs, and quality-assurance state. The unit of analysis is a selected-build bundle rather than a mutable installed-app label. Because popular apps may update during an evidence-collection wave, we use a fixed 14-day evidence window as a provenance and build-alignment control rather than as a longitudinal repeatability experiment. At cutoff, all 15 apps had static and runtime build-backed evidence. The main contributions are:
\begin{itemize}
    \item a 15-app static-runtime analysis with exact selected-build provenance;
    \item a recent-evidence cutoff that keeps versioned measurements valid under app-store updates;
    \item separate reporting of strict-idle, QFG, and interactive runtime classes;
    \item descriptive profiles that compare static exposure with runtime behavior as risk-posture dimensions, without an opaque composite score.
\end{itemize}
